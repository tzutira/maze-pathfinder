# Совместная работа в GitHub

Инструкция для команды из трёх человек. Код и документы хранятся в одном репозитории. GitHub хранит историю изменений, а VS Code используется для редактирования локальных файлов.

## Один раз для владельца репозитория

1. Войти в свой аккаунт GitHub. Выбрать **New repository**, имя `maze-pathfinder`, видимость **Public**, включить создание README и нажать **Create repository**. Не добавлять отдельный шаблон `.gitignore`: он уже подготовлен.
2. Установить GitHub Desktop с [официального сайта](https://desktop.github.com/) и войти в тот же аккаунт.
3. В GitHub Desktop выбрать **File → Clone repository**, выбрать созданный репозиторий и локальную папку. На этом компьютере удобно разместить его в `/Users/tzutira/Desktop/maze-pathfinder`.
4. Скопировать в клонированную папку содержимое подготовленного комплекта: `README.md`, `docs/scope.md`, `CONTRIBUTING.md`, `.gitignore`, `.github/pull_request_template.md`. Заменить автоматически созданный README. Сохранить папки `docs` и `.github`; скрытые файлы тоже должны попасть в репозиторий.
5. В GitHub Desktop проверить список изменённых файлов, написать сообщение `Зафиксирован объём проекта`, нажать **Commit to main**, затем **Push origin**. Это начальная загрузка; последующая командная работа идёт через отдельные ветки.
6. На сайте репозитория открыть **Settings → Collaborators → Add people** и пригласить двух участников по их GitHub-логинам. Они должны принять приглашение. Публичность позволяет всем читать проект, но не даёт всем права записывать изменения.

## Один раз для каждого участника

1. Создать собственный аккаунт GitHub и принять приглашение владельца.
2. Установить GitHub Desktop, войти в свой аккаунт.
3. Выбрать **File → Clone repository** и клонировать общий репозиторий. У каждого участника будет своя локальная копия на своём компьютере.
4. Открыть эту папку в VS Code через **File → Open Folder**. В настройках GitHub Desktop можно выбрать VS Code внешним редактором.

## Работа над каждой задачей

1. Сначала завершить текущие изменения: сохранить их и сделать commit либо осознанно отменить ненужные правки. Не переключать ветки с несохранённой работой.
2. В GitHub Desktop переключиться на `main`, нажать **Fetch origin**, затем **Pull origin**, если кнопка появилась. Так локальная копия получает изменения команды.
3. Через **Current Branch → New Branch** создать ветку для одной задачи. Например: `feature/maze-generation`, `feature/path-search`, `feature/console-ui` или `docs/requirements`.
4. Изменить файлы в VS Code и проверить результат.
5. В GitHub Desktop просмотреть изменения, написать короткое сообщение о сути работы и сделать **Commit**. Commit сохраняет версию локально.
6. Нажать **Publish branch** для первой публикации ветки или **Push origin** для последующих изменений. Push отправляет сохранённые версии на GitHub.
7. Создать **Pull Request** своей ветки в `main` через GitHub Desktop или сайт. Кратко указать, что изменено и как проверено. Запросить просмотр другим участником.
8. После просмотра и исправлений объединить изменения кнопкой **Merge pull request**. Автоматическое требование чужого одобрения отдельно не настроено: пока это правило команды.
9. После объединения переключиться на `main` в GitHub Desktop и получить обновления. Удалить завершённую ветку после того, как убедились, что её работа вошла в `main`.

## Четыре термина

| Термин | Значение |
| --- | --- |
| Branch, ветка | Отдельная линия изменений для конкретной задачи |
| Commit | Сохранённая версия изменений с пояснением |
| Push / Pull | Отправка своих версий / получение версий команды |
| Pull Request | Предложение проверить и объединить изменения ветки |

## Правила команды

- Каждую задачу завести в разделе **Issues**: цель, ожидаемый результат, ответственный. Имена участников подставить после распределения ролей.
- `main` содержит общую принятую версию. Для новых задач создавать ветки от обновлённой `main`.
- По возможности не менять одновременно один и тот же участок файла. Общие структуры и интерфейсы согласовать до параллельной реализации.
- Если GitHub сообщает о конфликте, не объединять изменения вслепую. Авторы согласуют итоговый текст или код; после разрешения проверяют результат ещё раз.
- В каждом Pull Request указывать, что и как проверено. Изменение алгоритма должен посмотреть другой участник.
- Хранить редактируемые требования и описания в Markdown, чтобы видеть различия между версиями. Итоговый PDF формировать после согласования документации.
- Не добавлять результаты сборки, пароли и токены. Личные сведения для титульного листа учебного PDF не требуется публиковать в репозитории.

## Предлагаемые зоны работы

1. Участник 1 — модель лабиринта и DFS.
2. Участник 2 — BFS, восстановление пути и проверки.
3. Участник 3 — интерфейс, отображение и объединение компонентов.

Проверка изменений по кругу: 1 смотрит работу 2, 2 — работу 3, 3 — работу 1. Требования и диаграммы обсуждают все трое.
